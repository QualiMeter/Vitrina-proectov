# Участие в разработке

1. Обновите `main` и создайте от неё временную ветку `feat/<scope>` или `chore/<scope>`.
2. Делайте обычные функциональные PR в `main`. Заполните шаблон PR, приложите скриншоты изменений интерфейса и укажите ограничения.
3. Для изменений frontend из каталога `frontend/` запустите `npm ci`, `npm run lint`, `npm run typecheck`, `npm run test:coverage`, `npm run build` и `npm run test:e2e` перед PR. Дождитесь автоматических проверок `quality`, `unit-tests`, `build` и `e2e`. Подробности — в `docs/ci-cd.md`.
4. Запросите review: для бизнес-изменений — у тимлида, для API/БД — у backend-владельца, для frontend — у `@Mouse-ai`. Ruleset `Main Integration Protection` пока допускает 0 approvals, поэтому это **обязательное правило команды, но не технически принудительное ограничение GitHub**. Запрещены прямые push в защищённую `main` и обход проверок.
5. Используйте токены из `frontend/src/app/styles/tokens.css` и существующий UI kit. Новые визуальные паттерны добавляйте в общую систему после согласования с командой.
6. Не придумывайте backend endpoints и не имитируйте авторизацию. Новые контракты берите из согласованного OpenAPI. Разрешения проверяйте на уровне действия и объекта; сервер остаётся источником истины.
7. Не коммитьте секреты, `.env` и персональные данные.

## Ответственные за merge

**Владелец frontend — @Mouse-ai.** Все PR, затрагивающие `frontend/` (включая frontend-конфигурацию, UI, API-клиент и e2e), объединяет в `main` только он. Остальные разработчики frontend не нажимают Merge и не включают Auto-merge; после CI и ревью передают PR ему. В смешанных frontend/backend PR также действует это правило; желательно разделять изменения.

**Backend-разработчик вправе самостоятельно мержить свои PR**, затрагивающие `backend/`, а также сопровождаемый им контракт `docs/api/openapi.yaml`, после CI, review при изменении бизнес-правил и согласования с тимлидом. Для существенного изменения схемы/DTO предварительно уведомляет FE-A/B/C. Документация и инфраструктура, не затрагивающие frontend, объединяются ответственными за свои области после ревью по договорённости.

Право Merge не отменяет обязательное ревью, CI, проверку конфликтов и права тимлида на принятие бизнес-решений. GitHub Ruleset пока не гарантирует эксклюзивность merge по каталогам; это правило команды, а для технического ограничения нужны дополнительные настройки и модель прав.

## Выпуск в Production

После review и успешных обязательных проверок ответственный за соответствующую область объединяет PR в `main` (для любого изменения `frontend/` — только `@Mouse-ai`). Это обновление основной Production-ветки: Git-интеграция Vercel автоматически создаёт Production Deployment фронтенда из `main`. Проверьте результат сборки и опубликованные маршруты. Отдельный release PR в `frontend` больше не нужен. Изменения, не затрагивающие каталог `frontend/`, Vercel может пропускать как не влияющие на сборку.

Git-ветки содержат снимки всего репозитория. Наличие `backend/` в `main` не запускает серверную часть: Vercel Root Directory — `frontend`. Backend-приложение, его CI и деплой появятся отдельно после согласования архитектуры. Ветка `frontend` теперь историческая, для релизов и новых PR не используется.

Ruleset `Main Integration Protection` требует PR и успешные проверки `quality`, `unit-tests`, `build`, `e2e` для `main`, запрещает force push и удаление ветки. Старый `Frontend Protection` пока сохранён для исторической ветки `frontend`, но не участвует в релизах. `CODEOWNERS` появится после определения GitHub-аккаунта реального техлида; число обязательных approvals рассматривается отдельно.
