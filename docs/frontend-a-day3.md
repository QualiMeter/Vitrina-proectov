## Навигация и сценарии

Главная → «Войти» → «Кабинет компании — демо» → «Открыть демонстрацию» →
«Управление кейсом». Это явный вход в демонстрацию, без имитации реального входа.
В кабинете доступны условия, этапы/точки, заявки и управление набором/запуском.

Шесть фиктивных кейсов покрывают DRAFT, REVISION, APPROVED,
REGISTRATION_OPEN/SELECTIVE, REGISTRATION_CLOSED и REGISTRATION_OPEN/OPEN.
Данные хранятся в памяти конкретной демонстрации. Перезагрузка или смена
сценария сбрасывает изменения. Сценарии: normal, empty, error, denied,
read-only, save-error и conflict. Ошибки не стирают введённый текст.
Обновление версии выполняется только по явному действию пользователя.

Маршруты: `/company/cases/:caseId/manage`, `/stages`, `/applications`,
`/applications/:applicationId` относительно того же caseId.
Публичные, студенческие и служебные маршруты сохранены.

## Контракты и подключение

DTO генерируются из актуального OpenAPI:

```powershell
npm run codegen:company
npm run check:company-contracts
```

Команды выполняются из frontend. Проверка drift добавлена в quality CI.
Парсер js-yaml явно объявлен devDependency с уже имеющейся в lock-файле версией.
Генератор даёт compile-time типы, но условные правила схемы дополнительно
проверяются в mock-репозитории и должны проверяться сервером.

WorkflowRepository соответствует операциям `stagesListForEditor`,
`stagesCreate/Update/Delete`, `checkpointsCreate/Update/Delete`,
`applicationsListForCompany`, `applicationsGet`, `applicationsDecide`,
`studentsGetCompanyVisibleProfile`, `casesCloseRegistration`, `casesStartExecution`.
Реализация пока полностью демонстрационная, HTTP-запросы не выполняются.

Версии: этапы/точки — expectedCaseVersion и expectedVersion; close-registration —
expectedVersion; start-execution — expectedCaseVersion. Решение заявки использует
expectedVersion и отдельный Idempotency-Key, который сохраняется при повторе
того же запроса и не переиспользуется для изменённого решения. Повтор не занимает
ещё одну квоту. Приватные инструкции и company-профили не передаются в публичные страницы.

Permissions в CaseSnapshot и `demo:decide` — локальные признаки демонстрации,
не согласованный словарь server allowedActions. Адаптер реального API должен
использовать реальные сессию, членство и объектные права и работать fail-closed,
если сервер не предоставил необходимые разрешения.

### Обнаруженные блокеры реального API

1. `backend/Vitrina.Api/Features/Applications/ApplicationEndpoints.cs` возвращает
   allowedActions объектом `{canEdit, canSubmit, canWithdraw}`, тогда как OpenAPI
   требует string[]. Нет контрактного разрешения на решение компании.
2. `CaseEndpoints.ToPrivate` не возвращает обязательные для CaseDraft
   createdByUserId, createdAt, updatedAt и allowedActions. Статус доработки backend
   `REVISION_REQUIRED` расходится с контрактным `REVISION`.
3. Код этапов/точек и API существуют, но полный локальный запуск backend с
   зависимостями, cookie/CSRF, тестовыми членствами и PostgreSQL здесь не подтверждён.
   Наличие кода в main не означает проверенную интеграцию.
4. FA-14: в контракте нет типа проверки, даты защиты, места и URL встречи.
   Эти поля не добавлялись в DTO и не отправляются фиктивным endpoint.
5. Backend start-execution требует хотя бы этап и контрольную точку. Нулевая
   стадийность из ТЗ и независимая финальная сдача требуют согласования модели;
   демо для запуска следует существующей проверке backend.
6. Company-профиль даёт publicSummary как описание опыта, но не структурированную
   историю прошлых работ. Полнота портфолио зависит от отдельного раздела FE-B.

NuGet-ошибки загрузки Testcontainers/EF/Redis/Scalar на ноутбуке относятся к
восстановлению backend и не означают ошибку TypeScript. Для работы с этим UI
можно открыть только frontend в VS Code; отключать TLS-проверки не требуется.
