# OpenAPI v0.1 — решения и замечания к согласованию

**Статус:** единый проект контракта `0.1.4-draft` (90 операций); ранее утверждённые параметры авторизации согласованы, API не опубликован и не реализован в backend.
**Путь после включения в репозиторий:** `docs/api/openapi.yaml`.
**Область текущей версии:** Auth, Companies, Cases, Teams, Applications, Stages, Checkpoints, Execution, Submissions, Files, NDA, Evaluation, Results, StudentProfiles, ReferenceData. Следующие расширения — портфолио, инициативы и другие модули **того же** контракта. Исходные бизнес-решения об Auth не изменялись.

## Согласованные решения

1. Серверные `HttpOnly` cookie-сессии, без JWT в `localStorage`. Production-cookie: `__Host-vitrina_session`, `Secure`, `SameSite=Lax`, `Path=/`, без `Domain`.
2. Несколько глобальных ролей для одного аккаунта плюс объектные полномочия. Капитан — член команды конкретного кейса; куратор — назначение; компания — членство.
3. Компания создаётся уполномоченным сотрудником УУНиТ. Приглашение на email принимает как существующий пользователь, так и новый. У нового email берётся из приглашения.
4. Обязательное подтверждение email студента при самостоятельной регистрации. Для этого нужен сервис отправки системных писем.
5. **Новый пароль: от 8 до 128 символов**, без обязательных требований к классам символов. Серверное хеширование, ограничение попыток входа, проверка по списку известных слабых/скомпрометированных паролей.
6. Приглашение в компанию действительно **7 дней**, токен сброса пароля — **30 минут**.
7. Серверная сессия действует не более **12 часов бездействия** и **7 дней с момента выдачи**; отзыв на logout/reset/block.
8. Представителей компании приглашает уполномоченный сотрудник УУНиТ либо член компании с разрешением `companies.invite`.
9. Браузер обращается к `/api/v1` через **единый origin** с frontend (reverse proxy на ASP.NET Core). Для изменяющих запросов обязателен CSRF-токен `X-CSRF-Token`.

## Детали, которые остаются на техническое согласование

| Вопрос | Предложение в YAML | Статус |
|---|---|---|
| Глобальные роли | `STUDENT`, `UNIVERSITY_STAFF`, `PLATFORM_ADMIN`; роль компании через членство | Уточнить права внешних кураторов и сотрудников. |
| Уникальность email | Сравнение без учёта регистра, один аккаунт на email | Согласовать смену адреса. |
| Данные студента | ФИО обязательно; институт, курс и группа необязательны на регистрации | Проверить требования перед подачей на кейс. |
| Длины остальных полей | Имя 2–200, компания 2–200, описание ≤5000, email ≤254 | Утвердить при DTO-review. |
| Подтверждение email | Срок токена **предлагается 24 часа** | Срок пока не согласован. |
| Формат ошибок | `code`, `message`, `requestId`, `fieldErrors`; 400/401/403/404/409/422/429 | Сверить с реализацией ASP.NET Core. |
| Обязательные поля компании | Название, описание, контактный email | Проверить с ТЗ и frontend. |
| Реестр компаний | Приватный реестр для УУНиТ, отдельная публичная карточка | Сверить матрицу прав. |
| Cookie на localhost | Для production `__Host-` и HTTPS, для разработки отдельный конфиг | Уточнить локальную схему и proxy. |
| «Запомнить меня» | Пока не добавлено | Не входит в согласованные возможности v0.1. |

## Что API должен проверять на сервере

- **Никогда** не принимать `globalRoles`, `availableAreas`, `companyId` или `membershipRole` из формы самостоятельной регистрации.
- **Никогда** не считать клиентский `PermissionGate` защитой от действий: членство, статус аккаунта, права на компанию и кураторские/командные назначения проверяются для каждого запроса.
- Приглашение: токен непредсказуемый, хранить только хеш; email проверять, токен принимать лишь один раз; создать членство атомарно; существующий пользователь обязан быть аутентифицирован.
- Для `register`, `forgot`, `resend`, `login`, `invitation/preview` — rate limiting; ответы `forgot/resend` одинаковы для существующих и несуществующих адресов.
- На `reset-password` — отзыв всех текущих сессий. На `logout` — отзыв текущей сессии и удаление cookie.
- Не хранить токены сброса и приглашения в логах, аналитике или URL backend. Ссылки письма на frontend следует открывать с `Referrer-Policy: no-referrer`; token после чтения удалять из адресной строки.
- `__Host-` cookie требует HTTPS (кроме специальных правил браузера для localhost); для локальной разработки согласовать HTTPS или отдельную конфигурацию cookie.

## Пример запросов

Запросить CSRF до входа:

```http
GET /api/v1/auth/csrf
```

```json
{ "csrfToken": "<request-token-from-backend>" }
```

Вход, браузер сам отправит сопутствующие cookies:

```http
POST /api/v1/auth/login
Content-Type: application/json
X-CSRF-Token: <request-token-from-backend>

{ "email": "student@example.com", "password": "example-password" }
```

После успешного входа: `GET /api/v1/auth/csrf` ещё раз, затем `GET /api/v1/auth/me`.

Принять приглашение для уже существующего пользователя:

```json
{ "mode": "existing", "token": "<invitation-token>" }
```

Для нового:

```json
{
  "mode": "new",
  "token": "<invitation-token>",
  "fullName": "Иван Иванов",
  "password": "correct-horse-battery-staple",
  "privacyAccepted": true,
  "privacyPolicyVersion": "v1"
}
```

## Расширение 0.1.1-draft: Cases / Teams / Applications

**Основное расположение:** `docs/api/openapi.yaml` — один файл; описание предметной модели: `docs/architecture/cases-teams-applications.md`.

### Пользователем утверждены

1. Капитана команды кейса можно сменить **только через отдельную процедуру с подтверждением**. Предлагаемая схема DTO: действующий капитан создаёт предложение, новый подтверждённый участник принимает/отклоняет его; фактический момент перехода прав — подтверждение и транзакционная фиксация.
2. После отзыва заявки **повторная подача в тот же кейс запрещена**. Запрет нельзя обходить сменой формата или команды, а история не стирается.
3. Приглашение в **команду кейса** действует не позднее закрытия набора (включая дедлайн) и не может быть принято после отправки командной заявки. Это правило **не равно** ранее согласованным семи дням для приглашений в компанию.

### Технические проектные решения в YAML, требующие review

- URL методов и DTO (`CaseDraft`, `CaseTeam`, `CaseApplication`); API не реализован. Для UI центра приглашений добавлены `GET /api/v1/me/team-invitations` и ограниченный поиск студентов `GET /api/v1/teams/{teamId}/invite-candidates` без приватных контактов. Решение о капитанстве объединено в один `POST .../captain-transfer/{transferId}/decision` с `CONFIRM/DECLINE`.
- `OPEN` автоматически допускает команду/solo **в момент подачи** при доступной квоте; `SELECTIVE` оставляет `SUBMITTED` без занятия квоты до ручного решения.
- `expectedVersion` в PATCH и изменяющих командах; обязательный `Idempotency-Key` для `applicationsSubmit/Withdraw/Decide`.
- Приглашение принимает только адресат; подтверждение капитанства — только новый капитан. Матрица прав во время выполнения кейса требует отдельного согласования.
- Сопроводительное письмо считается обязательным при `SELECTIVE`; сервер возвращает вычисленный `coverLetterRequired`.
- Черновик кейса при создании требует только название; полноту данных сервер проверяет при отправке на модерацию.
- Применение постоянного запрета повторной заявки ко всем участникам отозванной командной заявки — рекомендуемая защита от обхода, требует явного acceptance-теста.

### Не согласованы с заказчиком

Повторная заявка после `REJECTED` (в отличие от `WITHDRAWN`); лимиты по курсам и численности команд; безлимитные квоты; изменения состава после отправки; перенос капитанства на поздних стадиях; точные максимальные длины текстов, политика календарного закрытия набора и уведомлений. Включить эти решения в review до фиксации миграций.


## Расширение 0.1.2-draft — выполнение и файлы

Контракт в `docs/api/openapi.yaml` дополнен этапами, контрольными точками, версиями сдач, ручным отбором и доступом к приватным файлам (26 новых HTTP-операций). Источник бизнес-правил — пятидневный план, приложения B/E/F, BE-16—21; детали в `docs/architecture/execution-submissions-files.md`.

**Решения без изменения:** отсутствие автоматического запуска/отбора; допускается просроченная сдача до ручного закрытия; сохранение версий и истории; запрет выбывшим на будущие закрытые материалы; объектные права проверяются backend.

**Предложения, ещё не утверждённые пользователем:** схема `CaseStage` + `CaseCheckpoint`, единая финальная точка, stream через backend, личное NDA-подтверждение, staged upload, параметры доступности этапа. Особый BLOCKER: отбор соло в кейсе с SOLO/BOTH. Нельзя считать эти предложения утверждёнными положениями исходного ТЗ.


## Расширение v0.1.3-draft — финал, отзывы и призовые места

- Сохранены 75 ранее описанных операций. Добавлено 10 операций: запуск оценивания, приватная сводка, отзывы, ручные призовые места/номинации, публикация результатов, публичный и личный итог, аудит. Итого **85 операций, 137 схем**.
- По пятидневному плану подтверждены принципы: отзыв в тексте + необязательная оценка, ручные победители, совместные места только по опубликованным правилам EVAL-11, результаты доступны после подтверждения компании.
- Для проверки EVAL-11 предложены структурированные `CaseContestRules` (в т.ч. `allowSharedPlaces`) и `SaveAwardsDraftRequest`. Это **технический проект**, не дословные поля заказчика; согласовать при review.
- Статусы `FINAL_CLOSED → EVALUATING → COMPLETED`. До завершения компании не публикуем личные отзывы/баллы; после — публично только разрешённые места/номинации.
- Детали в `docs/architecture/case-evaluation-results.md`, примеры в `docs/api/REQUEST-EXAMPLES.md`.
- **Не утверждено:** соло-отбор, обязательность личной подписи NDA каждым членом, право на результат для исключённых/выбывших, обязательность отзыва каждому участнику, публикация имени без отдельного согласия, допустимая шкала баллов и правила исправления опубликованного результата.

 
## Дополнение 0.1.4-draft — сверка P0 с планом v2.1

Добавлено **5 операций и 8 схем** для профиля, публичной карточки студента, списка его участий и read-only справочников. Новые поля — проектные DTO для review, не утверждение о реализации backend. Остальные 85 операций и согласованные решения не менялись.

Срок приглашения в компанию — **7 дней**, как ранее утверждено. В приложении L пятидневного плана указаны предлагаемые 72 часа и прямо требуется согласование; это не основание молча менять действующий контракт. То же относится к условным URL из плана: в спецификации сохраняется `/api/v1`.

После отзыва заявления повторная подача запрещена: формулировку приложения D «по правилам» нельзя понимать как разрешение повторного участия. Смена капитана требует отдельного подтверждения, а приглашения в команду ограничены закрытием набора/подачей заявки. Это уже было описано в 0.1.1.

Контракты P1 ещё **не созданы**; см. `docs/api/PLAN-V2.1-ALIGNMENT.md`. Для их утверждения нужны исходное ТЗ, согласование TL и проверки FE-разработчиков. Пользовательское предположение о пяти рабочих днях не заменяет решение заказчика.
