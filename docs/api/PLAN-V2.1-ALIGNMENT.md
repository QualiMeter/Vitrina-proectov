# Сверка OpenAPI и плана VITRINA_5_DAYS_PLAN_v2_1

**Статус:** рабочий реестр отличий, версия 30.10.2026. Источник плана — предоставленный Word-файл. Контракт API проектный, backend пока не реализован. По спорным условиям требуется решение ответственного за ТЗ/тимлида.

## Подтверждённые изменения в текущем OpenAPI 0.1.4-draft

| План | Статус API до сверки | Что сделано |
| --- | --- | --- |
| FB-01/02 — просмотр/редактирование своего профиля | Не было endpoint | `GET/PATCH /api/v1/me/student-profile`; `StudentProfilePrivate`, `StudentProfileUpdateRequest`, expectedVersion |
| FB-03 — публичная карточка студента | Не было endpoint | `GET /api/v1/public/students/{studentId}`; отдельный `StudentProfilePublic` без приватных данных |
| FB-04/11 — мои участия/черновики | Не было агрегированного endpoint | `GET /api/v1/me/case-participations`; роль, формат, статусы, пагинация |
| BE-05, FA-04, FB-02, FC-09 — справочники для форм | Не было read-only endpoint | `GET /api/v1/reference-data`; опубликованные направления, технологии, компетенции, институты, категории |

Это **предварительные технические DTO**, нуждающиеся в ревью со стороны backend, FE-B и тимлида; не утверждённые требования заказчика. Названия девяти категорий портфолио в этих DTO не выдумывались.

## Различия, которые НЕ являются основанием для изменения согласованного API

| В плане v2.1 | В OpenAPI/ADR | Решение при сверке |
| --- | --- | --- |
| В день 1 согласовать OpenAPI v0.2 | Развитие P0 идёт по версиям 0.1.x-draft | 0.2 — целевой этап для P1, текущая версия 0.1.4 не переименовывается без полного покрытия |
| Условные URL `/api/auth/...` (приложение L) | `/api/v1/auth/...` | План прямо пишет, что URL предложены, не утверждены; сохраняем согласованный префикс |
| Предлагаемый TTL приглашения компании — 72 часа | Утверждено 7 дней | Не меняем без официального решения; срок в плане явно помечен «утвердить в день 1» |
| Минимальная длина пароля не везде повторена | 8–128 символов | Уже есть в схеме Password, корректировка не нужна |
| «Отзыв и создание новой» в приложении D | После WITHDRAWN повторное участие в кейсе запрещено | Сохраняем однозначный запрет, включая смену команды или SOLO/TEAM |
| Правила капитанства и срока командных приглашений описаны кратко | Смена капитана с подтверждением; срок приглашения — до закрытия набора и подачи заявки | Уже есть методы/DTO в 0.1.1; плану нужна детализация, не переписывание API |

## Реальный открытый объём BE-32: P1 (в 0.1.4 ещё НЕ покрыт)

Текущая спецификация содержит 90 операций и **не покрывает контрактами** перечисленные ниже P1-модули пятидневного плана. Для каждого нужно совместно утвердить DTO, enum, права, статусы и operationId, прежде чем разрешать frontend считать его Done (API).

| Ответственный API | Потребители | Недостающие области для следующего расширения |
| --- | --- | --- |
| BE-22 | FB-19—21, FC-17—18 | PortfolioWork: девять утверждённых категорий, приватный CRUD, публичный каталог, модерация, замечания |
| BE-23/24 | FB-22—28, FA-28, FC-17—18 | StudentInitiativeProject, два независимых статуса, команда, роли, заявки, решения автора, публичный контакт |
| BE-26 | FA-25/26, FC-13 | CompanyProductProject: закрытая карточка/команда, адресные приглашения, минимальный состав, ручной старт, сдача, приёмка |
| BE-27 | FA-27—29 | Публичный поиск студентов, фильтрация инициатив, избранное и изолированные по компании приватные заметки |
| BE-28 | FC-19—22, FB-29 | Объектные назначения/снятие кураторов, доступ только к назначенным проектам, комментарии и аудит |
| BE-29 | FC-25—27 | Пользователи/блокировки, управление справочниками, защищённый неизменяемый аудит |
| BE-30 | FC-28 | Шесть групп агрегатов и экспорты CSV/XLSX/PDF по ТЗ |
| BE-31 | FB-30 | Дополнительные уведомления и отметки о прочтении; не путать с обязательной системной почтой BE-34 |

**Принцип:** не добавлять догадочные полноценные P1-эндпоинты только ради цифры «v0.2». Параллельной UI-разработке допустимы только явно предварительные mock DTO в статусе UI Ready. Приоритеты P0/P1 — из плана, не автоматическое подтверждение приоритетов заказчиком.

## Вопросы к владельцу ТЗ/тимлиду до расширения

1. Применяются ли отборочные контрольные точки к SOLO и как именно выбирать прошедших?
2. Кто принимает NDA: каждый участник команды или только капитан? Когда оно требуется?
3. Как можно менять состав команды после подачи заявки, а также капитана во время исполнения?
4. Можно ли подавать повторную заявку после REJECTED (не путать с WITHDRAWN, для которого запрет уже утверждён)?
5. Какие именно девять категорий работ и шесть групп аналитики предусмотрены исходным ТЗ?
6. Какой набор академических данных/ссылок разрешён в публичном профиле студента; какие поля оставлять приватными?
7. Кто утверждает предлагаемые размеры, обязательность полей и права P1, поскольку план распределения сам по себе не источник бизнес-требований?

## Приёмка и ограничения пятидневного плана

В документе сроки frontend и backend местами разнесены: FB-07—12 нужны API дня 3, хотя UI выполняется в день 2; FB-13—18 опережают API дня 4. На день UI-готовности ставить только **UI Ready**, а **Done (API)** — после backend-интеграции, проверки безопасности и подтверждённого сценария.

До включения изменений в `main` актуальная спецификация находится в ветке `docs/openapi-p0-contract-v0.1`; сам backend-продукт в `backend/` пока не реализован.
