# Vitrina — Stage 3 implementation notes

## Included

- Case stage and checkpoint configuration with optimistic case/stage/checkpoint versions.
- Manual transition from `REGISTRATION_CLOSED` to `EXECUTING`.
- Participant workspace with future-stage filtering, current NDA check and private material metadata.
- Company execution dashboard.
- Manual selection for team IDs and solo application IDs. No score-based automatic selection.
- Manual closure of regular and final intake, plus team exclusion with a reason and audit entry.
- Immutable submission versions with `expectedLastVersion` and `Idempotency-Key`.
- Private MinIO object storage, metadata in PostgreSQL, server-side file streaming, per-request authorization and `Cache-Control: no-store`.
- Immutable NDA policy-version history and atomic acceptance by the solo applicant or current team captain during application submission.

## API request examples

Create a stage:

```json
{
  "expectedCaseVersion": 4,
  "title": "Разработка прототипа",
  "kind": "WORK",
  "sequence": 1,
  "description": "Основной этап разработки"
}
```

Create a selection checkpoint:

```json
{
  "expectedCaseVersion": 5,
  "title": "Промежуточный отбор",
  "kind": "SELECTION",
  "deadline": "2026-12-01T18:00:00Z",
  "selectionLimit": 5,
  "soloSelectionLimit": 2,
  "instructions": "Загрузите демонстрацию результата"
}
```

Submit a new immutable version (the first version uses `expectedLastVersion: 0`):

```http
POST /api/v1/checkpoints/{checkpointId}/submissions
Idempotency-Key: <unique-client-generated-key>
X-CSRF-Token: <csrf-token>
```

```json
{
  "applicationId": "00000000-0000-0000-0000-000000000001",
  "expectedLastVersion": 0,
  "description": "Первая версия результата",
  "links": [],
  "fileIds": []
}
```

## Storage security and operational boundaries

- MinIO bucket is private and is not published by Docker Compose. The API never returns a public or presigned object URL.
- Object keys are generated by the server; the original filename is metadata only.
- Uploads are limited by `Storage:MaxFileSizeBytes` (`STORAGE_MAX_FILE_SIZE_BYTES` in the deployment environment), default 25 MiB.
- Supported initial types: PDF, PNG, JPEG, TXT, DOCX, XLSX and PPTX. The server checks the extension and a basic file signature.
- The implementation does not include antivirus/malware scanning, CDR or deduplication. A background cleanup removes unbound `READY` uploads and failed/incomplete uploads after 24 hours. A `READY` status means the upload and basic signature checks completed, not that a file is malware-free.
- Submission attachments remain private until attached to a submission version. Stage materials become visible only after binding and when the participant's execution stage is available.
- File content is streamed through the API after authorization; private responses are `no-store`.

## Existing database upgrade

Apply `deploy/postgres/003_stage3_execution_submissions_files.sql` to an existing Stage 2 PostgreSQL database before starting the Stage 3 API. It is idempotent for the Stage 3 objects/columns. A new empty database uses the current EF model. `EnsureCreated` does not migrate existing schemas.
