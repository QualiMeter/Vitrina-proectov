# Витрина ИТ-проектов — оценивание, отзывы, призовые места и результаты

**Контракт:** `docs/api/openapi.yaml`, версия `0.1.3-draft`. **Путь документа:** `docs/architecture/case-evaluation-results.md`.  
**Статус:** архитектурный проект для review; в репозитории backend пока нет реализации.  
**Основание:** пятидневный план `VITRINA_5_DAYS_CORRECTED.docx`, BE-21, FA-23/24, TL-21—25 и приложение F (EVAL-11). Первичное ТЗ v5.1 отдельно не проверено.

## 1. Бизнес-смысл

1. Компания после ручного завершения приёма финальных версий переводит кейс `FINAL_CLOSED → EVALUATING` отдельным действием.
2. Компания оставляет **текстовый отзыв** по заявке TEAM/SOLO; числовая оценка **необязательна**. Оценка не назначает победителей автоматически.
3. Компания **вручную** назначает призовые места и номинации допущенным заявкам, которые имеют право участвовать в итогах.
4. **Совместные призовые места** допускаются только если они разрешены **заранее опубликованными правилами конкурса** (EVAL-11).
5. После отдельного подтверждения компанией `EVALUATING → COMPLETED` результаты публикуются. До публикации ни гость, ни другие команды не видят черновые итоги, баллы или отзывы.
6. Публичная выдача содержит только опубликованные места/номинации и разрешённое имя команды или участника; **не** содержит частные отзывы, оценки, персональные контакты, закрытые файлы и метаданные.
7. Индивидуальный отзыв доступен после публикации только участнику своей заявки; компании доступна проверка отзывов и черновиков.
8. Любое изменение черновика отзывов/наград журналируется; после публикации изменения не выполняются обычными PUT. Исправление опубликованной ошибки требует отдельной процедуры (за пределами v0.1.3).

## 2. Предложенные DTO

| DTO | Основные поля | Ограничение |
|---|---|---|
| `CaseContestRules` | `allowSharedPlaces`, `prizePlaceCount`, `nominationNames`, `scoreRange?` | Условия публикации должны быть известны **до** модерации/начала конкурса. После публикации неизменяемы. Поля — проектное уточнение для машинной валидации. |
| `CaseScoreRange` | `min`, `max` | `min < max`, диапазон проверяется сервером. Оценка необязательна. |
| `ReviewDraftRequest` | `expectedReviewVersion`, `feedback`, `score?` | Обязательный текст; `score` может отсутствовать или быть null; 0 — ещё нет отзыва, N — изменение существующей версии. |
| `ApplicationReview` | `applicationId`, `feedback`, `score?`, `version`, `isPublished` | Не публичный DTO; право чтения — по заявке и состоянию. |
| `SaveAwardsDraftRequest` | `expectedAwardsVersion`, `placements`, `nominations` | Полная атомарная замена черновика. Дубли заявок/мест/номинаций валидируются сервером. |
| `PrizeAward` | `applicationId`, `place` | Номера мест от 1 до `prizePlaceCount`; несколько заявок на месте разрешены только при `allowSharedPlaces=true`. |
| `NominationAward` | `applicationId`, `nomination` | Только номинации из опубликованного списка. |
| `PublishResultsRequest` | `expectedCaseVersion`, `expectedAwardsVersion`, `confirm:true` | Явное необратимое подтверждение, идемпотентный POST. |
| `PublishedCaseResults` | `caseId`, `publishedAt`, `entries[]` | Только после `COMPLETED`; без чужих приватных данных. |
| `MyCaseResult` | `applicationId`, `review?`, `placements[]`, `nominations[]` | Выдаётся только своей заявке после публикации. |

### Машинная проверка EVAL-11

Если конкурс допускает места 1…3 и **не** допускает совместные места, две разные заявки с `place=1` дают `422` или `409` по утверждённой политике ошибок. При `allowSharedPlaces=true` это может быть допустимо, но только если правило было опубликовано до начала конкурса. Менять `allowSharedPlaces` на этапе оценивания **нельзя**. Победители не вычисляются из `score`.

`CaseContestRules` добавлен в черновик кейса, PATCH черновика и публичную карточку. Введение отдельной структурированной конфигурации вместо только текстового `rewardTerms` — **предложение по реализации**, не новое требование заказчика. Полнота и допустимость настроек проверяются на переходе в модерацию.

## 3. API-операции (10 новых)

| Метод | URL | operationId | Для кого |
|---|---|---|---|
| POST | `/api/v1/cases/{caseId}/begin-evaluation` | `casesBeginEvaluation` | Компания |
| GET | `/api/v1/cases/{caseId}/evaluation` | `casesGetEvaluationProgress` | Компания/уполномоченный УУНиТ |
| GET | `/api/v1/cases/{caseId}/reviews` | `casesListApplicationReviews` | Компания/уполномоченный УУНиТ |
| PUT | `/api/v1/cases/{caseId}/applications/{applicationId}/review` | `casesUpsertApplicationReview` | Компания |
| GET | `/api/v1/cases/{caseId}/awards` | `casesGetAwardsDraft` | Компания/уполномоченный УУНиТ |
| PUT | `/api/v1/cases/{caseId}/awards` | `casesSaveAwardsDraft` | Компания |
| POST | `/api/v1/cases/{caseId}/publish-results` | `casesPublishResults` | Компания |
| GET | `/api/v1/public/cases/{caseId}/results` | `casesGetPublicResults` | Гость после публикации |
| GET | `/api/v1/cases/{caseId}/results/mine` | `casesGetMyResults` | Свой участник после публикации |
| GET | `/api/v1/cases/{caseId}/evaluation-audit` | `casesGetEvaluationAudit` | Уполномоченные |

**Стандарт ответов:** 401 отсутствие сессии, 403 права, 404 объект скрыт/отсутствует, 409 устаревшая версия/состояние/повтор, 422 нарушение опубликованных конкурсных ограничений. Для изменяющих запросов обязателен `X-CSRF-Token`; для критичных переходов — `Idempotency-Key`.

## 4. Пример сквозного сценария

1. `POST /cases/{caseId}/close-final-intake` → `FINAL_CLOSED` (из 0.1.2).
2. `POST /cases/{caseId}/begin-evaluation` → `EVALUATING`.
3. `PUT /cases/{caseId}/applications/{applicationId}/review` с `feedback` и, опционально, `score`.
4. `PUT /cases/{caseId}/awards` с двумя независимыми массивами мест и номинаций. Сервер сравнивает с опубликованным `CaseContestRules`.
5. `GET /cases/{caseId}/evaluation` + `GET /cases/{caseId}/awards` для приватной проверки.
6. `POST /cases/{caseId}/publish-results` с `confirm:true` → `COMPLETED`.
7. `GET /public/cases/{caseId}/results` теперь доступен гостю; `GET /cases/{caseId}/results/mine` возвращает свой личный отзыв.

## 5. Тесты на приёмке

- [ ] Без завершённого финального приёма невозможно начать оценивание.
- [ ] Другой компании запрещено читать и изменять отзывы и черновики наград.
- [ ] Результаты для гостя скрыты до `COMPLETED` даже при прямом GET.
- [ ] Числовой балл не обязателен и не определяет место.
- [ ] Два победителя одного места запрещены при `allowSharedPlaces=false` и допустимы при `true` по опубликованным правилам.
- [ ] Номинации не добавляются вне опубликованного списка.
- [ ] После публикации обычный PUT отзывов/наград получает 409.
- [ ] Получить чужой личный отзыв/балл нельзя даже через подстановку applicationId.
- [ ] Сетевой повтор `publish-results` с тем же `Idempotency-Key` не публикует повторно/не дублирует уведомления.
- [ ] Изменения сохраняют audit trail, версии черновика защищены от гонок.

## 6. Решения, которые нельзя выдавать за утверждённое ТЗ

**Требуют TL/заказчика:** структура опубликованных призовых правил (`CaseContestRules`), допустимые диапазоны score и места/номинации, состав публичных имён и согласия на публикацию, может ли исключённая/выбывшая заявка получить отзыв или номинацию, обязательность отзыва каждой заявке перед публикацией, порядок исправления опубликованного итога.

**Открыты из предыдущих модулей:** SOLO на отборочной точке (в YAML дана *опциональная, не утверждённая* схема отдельной квоты `soloSelectionLimit` и выбора `passingSoloApplicationIds`); подпись NDA каждым членом команды; повтор после `REJECTED`; изменение состава после подачи; перевод капитана во время исполнения. Эти вопросы не закрыты автоматически новым модулем.

**Граница охвата:** корпоративный P0-цикл кейса описан в проекте контракта до `COMPLETED`. Портфолио, студенческие инициативы, закрытые продуктовые проекты, поиск, аналитика и уведомления по всему ТЗ ещё не добавлены; это P1 и отдельное продолжение. Никакой API пока не считается реализованным.
