# Витрина ИТ-проектов — корпоративные кейсы, команды и заявки

**Статус:** проект API v0.1.1-draft для review, не реализованный backend. **Путь в репозитории:** `docs/architecture/cases-teams-applications.md`.

**Источники:** пятидневный план `VITRINA_5_DAYS_CORRECTED.docx`: BE-07—15, FA-07—18, FB-07—12, приложения B, D и K; отдельно утверждённые пользователем решения о передаче капитанства, повторной заявке и сроках приглашений. Полный первичный ТЗ v5.1 отдельно пока не сверялся. Всё, что ниже отмечено как «проектное допущение», требует ревью команды, а не считается требованием заказчика.

## 1. Границы текущего расширения

Существующие Auth/Companies сохранены в **том же** `docs/api/openapi.yaml`. Добавлены `Cases`, `Teams`, `Applications`: публичная витрина кейсов, приватный кабинет компании, модерация, открытие/закрытие набора, команда и её приглашения, передача капитанства, черновик, подача/отзыв заявки, автоматический или выборочный допуск, история событий.

**Границы этого документа:** описывает первую предметную область — кейсы, команды, заявки. API этапов, контрольных точек, защищённых файлов, NDA, запуска, версий сдач и отбора уже добавлен отдельным расширением `0.1.2-draft`, см. `docs/architecture/execution-submissions-files.md`. Финальные результаты включены отдельным расширением 0.1.3 (`docs/architecture/case-evaluation-results.md`); портфолио/инициативы остаются вне текущего OpenAPI. Ни одна операция не означает готовность backend.

## 3. Утверждённые бизнес-правила

1. **Капитанство.** Смена разрешена только через отдельное действие. В предложенном API текущий капитан инициирует `captain-transfer`, новый подтверждённый участник команды принимает/отклоняет. До подтверждения текущий капитан сохраняет полномочия; в транзакции обновляются назначение и история. Передача не меняет автора старых заявок/сдач. Нуждается в review конкретная матрица доступности передачи после подачи заявки и во время исполнения.
2. **Отзыв заявки.** Состояние `WITHDRAWN` является конечным для повторной подачи на тот же кейс. Нельзя создать новую заявку в другом формате или через другую команду с теми же участниками после отзыва. Нельзя удалять историю, чтобы обойти запрет. Отзыв допускается до начала выполнения по правилам пятидневного плана.
3. **Приглашение в команду.** `PENDING` перестаёт быть действительным не позднее ручного закрытия набора/времени дедлайна (по реально действующему состоянию) и сразу после отправки соответствующей командной заявки. Вновь открытый набор не «оживляет» просроченные приглашения — требуется новое приглашение.
4. **Формат участия.** `participationFormat: SOLO | TEAM | BOTH` относится к настройке кейса. `format: SOLO | TEAM` — к одной заявке. TEAM содержит `teamId`, SOLO — определяемый сервером `soloApplicantUserId`; одновременно оба поля запрещены.
5. **Набор.** `OPEN` — автодопуск во время отправки заявки при достаточном лимите. `SELECTIVE` — компания вручную принимает либо отклоняет `SUBMITTED`; обязательное сопроводительное письмо при выборочном наборе. `coverLetterRequired` является вычисляемым полем (`admissionMode == SELECTIVE`), а не пользовательским переключателем.
6. **Квоты.** `maxAdmittedTeams` и `maxAdmittedSolo` независимы; `SUBMITTED` и `DRAFT` их не занимают. `null` означает квота не задана (возможность требует подтверждения заказчиком). Квота считается только по `ADMITTED`.
7. **Права.** Капитан создаёт и отправляет командную заявку, solo — собственную. Создать приглашение может капитан, принять — только адресат. Модерация — сотрудник УУНиТ, решение по выборочному набору — представитель компании с объектным правом. Правила проверяются backend в каждой операции.
8. **Редактирование.** Черновики сохраняются сервером; `expectedVersion` предотвращает молчаливую перезапись. После публикации существенные условия кейса нельзя менять обычным PATCH.

## 4. Статусы и переходы

### Корпоративный кейс

| Переход | Кто | Условия |
|---|---|---|
| `DRAFT`/`REVISION → MODERATION` | компания | Заполнены обязательные поля; проверка формата, срока, прав на результат |
| `MODERATION → APPROVED` | УУНиТ | Подтверждение модератором |
| `MODERATION → REVISION/REJECTED` | УУНиТ | Обязательная причина |
| `APPROVED → REGISTRATION_OPEN` | компания | Ручное открытие; опубликованные условия зафиксированы |
| `REGISTRATION_OPEN → REGISTRATION_CLOSED` | компания | Ручное закрытие набора |
| `REGISTRATION_CLOSED → REGISTRATION_OPEN` | компания | Только до начала выполнения с **новым более поздним дедлайном** |
| `REGISTRATION_CLOSED → EXECUTING → FINAL_CLOSED → EVALUATING → COMPLETED` | компания и backend | Это **будущие API-модули**; здесь определены только enum |
| `→ CANCELED` | по полномочиям | Правила отмены и аудит — отдельное решение |

### Команда и приглашение

`PENDING → ACCEPTED | DECLINED | REVOKED | EXPIRED`. Принятие атомарно добавляет членство после проверки на конфликт участия в том же кейсе. `DECLINED` сохраняется в истории, но отказавшийся не считается участником. Для подачи командной заявки не должно оставаться активных `PENDING` и иных неподтверждённых участников в заявляемом составе. Ожидающая передача капитанства (`CaptainTransfer: PENDING`) завершается только личным `CONFIRMED` новым капитаном, либо `DECLINED/CANCELED`.

### Заявка

- `DRAFT → SUBMITTED` для `SELECTIVE`.
- `DRAFT → ADMITTED` для `OPEN`, атомарно с занятием соответствующей квоты.
- `SUBMITTED → ADMITTED | REJECTED` — решение компании.
- `SUBMITTED/ADMITTED → WITHDRAWN` — допустимый отзыв до начала выполнения; состояние **конечное** для повторной подачи.
- После `REJECTED`, как и после `WITHDRAWN`, новая заявка того же участника в тот же кейс запрещена независимо от SOLO/TEAM и новой команды (решение тимлида).

При отзыве `ADMITTED` освобождение места допустимо, только если набор ещё открыт и выполняются условия плана. После закрытия набора автоматического переоткрытия нет. Повтор действия должен быть идемпотентен.

## 6. DTO и правила валидации

**Создание черновика кейса** (`CreateCaseDraftRequest`) требует только `title`, чтобы сохранять незавершённые формы. `UpdateCaseDraftRequest` позволяет заполнять описание, направления, технологии, сроки, ограничения, награды, права на результаты, лимиты команд и solo. Перед `submit-moderation` сервер проверяет завершённость. Для случаев `participationFormat=SOLO/TEAM` валидируются соответствующие размерности; `minTeamSize ≤ maxTeamSize`, `minCourse ≤ maxCourse`, дедлайн в допустимом будущем.

**Публичные DTO** (`CasePublicSummary`, `CasePublicDetails`) не содержат файлов, приватных этапов, персональных данных заявок. **Приватный DTO** (`CaseDraft`) возвращает версию, состояние и `allowedActions` как подсказку интерфейсу; последнее не заменяет серверной проверки.

**Команда** (`CaseTeam`) может менять участников до submit заявки: приглашения, выход участника или исключение капитаном; после submit состав неизменяем даже в REJECTED/WITHDRAWN. Подтверждаемая смена капитана — отдельный процесс и не разрешает менять список членов. Содержит подтверждённый состав, ожидающие приглашения (видимые только капитану) и текущую передачу капитанства. Входящие приглашения получаются отдельным `teamsListMyInvitations` со сведениями о кейсе, капитане и команде; `teamsSearchInviteCandidates` ищет только по публичным атрибутам без раскрытия email. `CaseTeamInvitation` отдельно хранит дату создания, `expiresAt` и ответ. **Заявка** (`CaseApplication`) содержит status, format, version, subject, coverLetter, фиксацию участников `participantUserIds`, timestamps, `allowedActions`.

**Обязательные ограничения из контракта:** согласованные `Id` как UUID, версия >= 1; лимиты >= 0 или `null` (до подтверждения), размер команды >= 1 (минимум для TEAM — предметная проверка), непустое название. **Проектные предложения, требующие review:** максимальные длины текстов, состав справочников, конкретные границы курса, поддержка безлимитных квот, политика повторной подачи после `REJECTED` **утверждена: запрет**.

### Пример: сохранить TEAM-черновик

```http
POST /api/v1/cases/{caseId}/applications
Cookie: __Host-vitrina_session=...
X-CSRF-Token: ...
Content-Type: application/json

{"format":"TEAM","teamId":"aaaaaaaa-aaaa-4aaa-8aaa-aaaaaaaaaaaa"}
```

### Пример: отправить черновик заявки

```http
POST /api/v1/applications/{applicationId}/submit
Cookie: __Host-vitrina_session=...
X-CSRF-Token: ...
Idempotency-Key: ui-submit-2026-001
Content-Type: application/json

{"expectedVersion":1}
```

При `OPEN` возможен ответ `200` с `ADMITTED`, при `SELECTIVE` — `200` с `SUBMITTED`. Если квота занята конкурентным запросом: `409` с кодом ошибки, **без изменения** исходного черновика.

### Пример: разрешить выборочную заявку

```http
POST /api/v1/applications/{applicationId}/decision
Cookie: __Host-vitrina_session=...
X-CSRF-Token: ...
Idempotency-Key: ui-admit-2026-001
Content-Type: application/json

{"action":"ADMIT","expectedVersion":2}
```

## 7. Транзакционные инварианты в PostgreSQL

- Уникальность подтверждённого членства `(case_id, user_id)` между командами (через денормализованный ключ или транзакционную блокировку/сопоставимую стратегию).
- Нельзя провести одного студента одновременно по solo и командной заявкам на один кейс; после отзыва сохраняется долговременная запись участия, чтобы повторная попытка завершалась `409`.
- Транзакция допуска захватывает общую квоту **конкретного кейса и формата**: при лимите 1 и двух одновременных принятиях успешен ровно один. В ответе проигравшего `409`, не `500`.
- `expectedVersion` не позволяет потерять изменения при параллельном PATCH/смене статуса.
- `Idempotency-Key` обязателен для `submit`, `withdraw`, `decision`; повтор с тем же телом и ключом возвращает прежний результат, другой payload при том же ключе — `409`. Ключ привязывать к аккаунту, operation и ресурсу.
- Публичные методы не отдают закрытые стадии, материалы, чужие заявки, email приглашённых и приватные комментарии.

## 8. Предлагаемая матрица прав

| Операция | Студент / капитан | Представитель компании | УУНиТ | Гость |
|---|---|---|---|---|
| Публичный каталог и карточка | Да | Да | Да | Да |
| Создать / изменить черновик кейса | Нет | Только своей компании с правом | Нет в чужом качестве | Нет |
| Одобрить / вернуть кейс | Нет | Нет | Да, уполномоченный | Нет |
| Открыть/закрыть набор | Нет | Только своего кейса | Нет, если нет объектного права | Нет |
| Создать команду / пригласить | Капитан своей команды | Нет | Нет | Нет |
| Принять приглашение | Только приглашённый | Нет | Нет | Нет |
| Отправить командную заявку | Только текущий капитан | Нет | Нет | Нет |
| Отправить solo-заявку | Только сам solo-студент | Нет | Нет | Нет |
| Принять/отклонить заявку | Нет | Только своей компании с правом | Нет | Нет |

Все права обязаны проверяться сервером с учётом роли, активного членства, статуса команды, кейса и контекста конкретного объекта. Уполномоченный УУНиТ может обладать дополнительными аудиторскими правами, если они явно согласованы; не давать blanket admin-доступ.

## 9. Сценарии тестирования

1. `Case DRAFT → MODERATION → APPROVED → REGISTRATION_OPEN` с правами компании/УУНиТ и отклонением неавторизованных действий.
2. Публичный каталог без черновиков/приватных вложений. Студенты не скачивают закрытые материалы через прямой URL (проверяется в следующем API-модуле).
3. Создать команду, пригласить студента, принять, успешно отправить TEAM-заявку только капитаном.
4. Приглашение в команду невозможно принять после подачи заявки или закрытия набора (а также после дедлайна).
5. Перевод капитанства: инициатор текущий капитан, новый лично подтверждает; без подтверждения капитанство не меняется, история не переписывается.
6. Соло-заявка; восстановление серверного черновика, конфликт concurrent `expectedVersion`.
7. SELECTIVE: `SUBMITTED` не занимает место; ручной допуск занимает только соответствующую квоту.
8. OPEN: автодопуск атомарно; два конкурентных запроса на последнее место — 1 успех и 1 `409`.
9. Раздельные квоты: занятие последней командной квоты не блокирует свободную solo-квоту.
10. Отозванная заявка остаётся в истории; повторное участие того же студента в данном кейсе после отзыва — `409` при смене команды или формата.
11. Отзыв `ADMITTED` до старта освобождает место по правилам, но не открывает автоматически закрытый набор.
12. Повторные команды с одним idempotency key не создают повторных изменений.

## 10. Решения, которые ещё нужны до backend миграций

- Правила изменения состава команды после подачи заявки, условия смены капитана на стадии исполнения.
- Повторная подача **после отклонения**, в отличие от уже запрещённой повторной подачи после отзыва.
- Численные пределы курса и размеров команды, значение отсутствующей квоты, обязательные поля форм из полного ТЗ v5.1.
- Кто вправе менять дедлайн и какие уведомления отправляются при повторном открытии набора.
- Согласование точных URL, DTO и серверных имен `enum` на ревью бэкендера/трёх фронтендеров.

Неразрешённые вопросы не означают, что команда вправе самостоятельно подставить бизнес-правило. Для них ставим `Decision needed`.

 
## Решения тимлида, подтверждённые в 0.1.5-draft

- Команду сначала создают, затем приглашают участников. До submit состав разрешено менять. `DELETE /api/v1/teams/{teamId}/members/{memberUserId}` — удаление участника капитаном или добровольный выход самого участника. Капитан должен сперва передать права через процедуру подтверждения, если хочет выйти.
- В момент `applicationsSubmit` фиксируется весь подтверждённый состав команды, после этого состав нельзя менять, включая отклонённую или отозванную заявку.
- Новый коллектив не даёт право прежнему участнику повторно подать на тот же кейс после REJECTED/WITHDRAWN. Ограничение проверяется по `caseId + userId` из истории участников.
- NDA, если обязателен, подтверждает только капитан TEAM (solo — сам заявитель) атомарно при submit. Самостоятельные подтверждения других участников команды не предусмотрены.
