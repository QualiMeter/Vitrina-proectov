# Витрина ИТ-проектов — этапы, контрольные точки, сдачи, защищённые файлы

**Версия:** OpenAPI `0.1.2-draft` (архитектурный проект, **не реализованный backend**).  
**Рекомендуемый путь:** `docs/architecture/execution-submissions-files.md`.  
**Единый контракт:** `docs/api/openapi.yaml` (текущая версия 0.1.5-draft: 94 HTTP-операции, 150 схем). Исторические сведения ниже относятся к первому проекту 0.1.2.

## 1. Основание и границы

**Из предоставленного пятидневного плана:** BE-16—20 (дни 4), BE-21 (ручное завершение приёма — день 5), FA-13/14/19—24, FB-13—18, TL-16—20, DO-06/07/16—19; приложения B/E/F. Исходное основное ТЗ v5.1 не предоставлено для отдельной сверки.  
**Уже утверждено пользователем в предыдущих этапах:** HttpOnly cookie + CSRF, несколько ролей/объектные права, приглашения компаний, передача капитанства с подтверждением, запрет повторной заявки после отзыва, окончание приглашений с закрытием набора/подачей командной заявки.

**Этот релиз описывает только контракт:** этапы и точки, рабочее пространство, старт выполнения, версии сдач, ручной отбор, приватные файлы, NDA-поток. **Не реализованы/не проектировались здесь:** отзывы, числовые оценки, призовые места/номинации EVAL-11, портфолио и студенческие инициативы; их предстоит отдельно специфицировать и реализовать. Включение endpoint в YAML не означает работающий сервер.

## 2. Модель данных и варианты DTO

| Объект | Идентификатор и связи | Главное правило |
|---|---|---|
| `CaseStage` | `id`, `caseId`, `sequence`, `version` | Последовательность этапов на кейс, изменение при `DRAFT/REVISION`. |
| `CaseCheckpoint` | `id`, `stageId`, `caseId`, `version`, `deadline`, `kind` | `REGULAR`, `SELECTION` (лимит проходящих команд N), `FINAL`; общий дедлайн для всех. |
| `SubmissionVersion` | `id`, `checkpointId`, `applicationId`, `version` | Исторические версии только добавляются, не перезаписываются. |
| `FileUploadResult` и `CaseFileMetadata` | `fileId`, цель и связанный case/stage/checkpoint/application | Файлы до привязки изолированы; скачивание через сервер, без публичного storage URL. |
| `NdaPolicy` / `NdaAcceptanceResult` | `caseId`, `version`, `userId`, `acceptedAt` | Текст доступен для ознакомления до подписания; факты принятия фиксируются. |

`CaseStage` и `CaseCheckpoint` — **отдельные сущности**: один этап содержит список контрольных точек. Наличие «этапов», «обычных и отборочных контрольных точек» следует из плана, а разбиение на две таблицы и строки перечислений `WORK`, `REGULAR`, `SELECTION`, `FINAL` — **наше проектное представление для ревью**.

В `GET /api/v1/cases/{caseId}/stages` компания и модератор видят полный состав, инструкции и привязанные метаданные файлов. Для студента предусмотрен **другой ответ** `GET /api/v1/cases/{caseId}/workspace`, из которого сервер полностью исключает недоступные будущие этапы, материалы и скрытые инструкции.

| POST | `/api/v1/cases/{caseId}/close-final-intake` | `casesCloseFinalIntake` |
| POST | `/api/v1/teams/{teamId}/exclude` | `teamsExcludeFromExecution` |

`casesStartExecution` допускает **только ручной** переход `REGISTRATION_CLOSED → EXECUTING` при наличии допущенных активных заявок. Запуск не даёт доступ к файлам сам по себе: повторно проверяются права команды, состояние отбора, доступность этапа и NDA.

После общего `deadline` `submissionsCreateVersion` продолжает принимать новые версии **с вычисляемым сервером** `isLate=true`, пока компания вручную не закроет соответствующий приём. Только капитан команды или сам соло-участник вправе сдавать результат. Версии не перезаписываются, запрещённые попытки дают 403/409. `Idempotency-Key` для повторов отправки не даёт удвоить версию.

`POST /api/v1/teams/{teamId}/exclude` — отдельное ручное исключение команды с обязательной причиной и историей, которое немедленно отменяет её права на будущие материалы и сдачи. Операция не стирает прежние версии.

`complete-selection` принимает `passingTeamIds` (до N) и транзакционно переводит невыбранные активные команды в «выбыли». После этого никакие новые версии на эту точку не принимаются и закрытые материалы будущих этапов для выбывших недоступны. **Автоматический отбор по баллам не допускается.** Результат своего отбора можно узнать отдельно; чужие заявки не видны.

`close-final-intake` фиксирует переход `EXECUTING → FINAL_CLOSED` и прекращение новых финальных версий. Последующие оценивание/победители пока вне данного расширения. Для `REGULAR` предусмотрено закрытие конкретной точки; для `SELECTION` его роль выполняет `complete-selection`. Это модель исполнения, требующая финального согласования с backend.

### Закрытые файлы и NDA — Backend + DevOps

| Метод | URL | operationId |
|---|---|---|
| POST | `/api/v1/files` (multipart) | `filesUpload` |
| GET | `/api/v1/files/{fileId}` | `filesGetMetadata` |
| GET | `/api/v1/files/{fileId}/content` (binary) | `filesDownload` |
| GET | `/api/v1/cases/{caseId}/nda` | `ndaGetPolicy` |
| POST | `/api/v1/cases/{caseId}/nda/accept` | `ndaAcceptPolicy` |
| PUT | `/api/v1/cases/{caseId}/nda` | `ndaConfigurePolicy` |

1. Для материалов компании файл загружается с `purpose=STAGE_MATERIAL`, `caseId`, `stageId`, проходит проверки и становится `READY`; после этого компания привязывает `fileId` к этапу.
2. Для сдачи студент загружает файл с `purpose=SUBMISSION_ATTACHMENT`, `caseId`, `checkpointId`, `applicationId`; `fileId` передаёт в команду сдачи новой версии. Привязка одноразовая, сервер проверяет автора, кейс и точку.
3. `QUARANTINED`/`REJECTED` нельзя привязывать как доступный контент. Максимальный размер, разрешённые MIME/расширения/сигнатуры, сроки очистки и антивирус — параметры конфигурации, **числа не придуманы без заказчика**.
4. Приватные файлы не лежат в `frontend/public/`, и не существует постоянных публичных ссылок на хранилище. `GET /files/{fileId}` и `GET /files/{fileId}/content` каждый раз проверяют права. Для приватного контента — `Cache-Control: no-store` и поток через backend. Так отзыв доступа не зависит от срока уже выданной signed URL.
5. При исключении/выбытии будущие материалы и их **метаданные** скрываются. Собственная история старых сдач сохраняется и доступна в рамках исторических прав; скачивание своих старых вложений — отдельное право, не означающее доступ ко всему кейсу.
6. `PUT /cases/{caseId}/nda` позволяет компании настроить текст и флаг обязательности в DRAFT/REVISION. Это техническое предложение для review; само требование NDA взято из плана. `NdaPolicy` содержит текст для ознакомления *до* принятия. Принятие сохраняет время, версию, текущего пользователя. По решению TL NDA в момент submit принимает только капитан TEAM или SOLO-заявитель; версия фиксируется в самой заявке. Принятие каждым членом команды не требуется.

Документация Microsoft для ASP.NET Core рекомендует проверять содержимое, размер, тип, не доверять пользовательским именам и хранить загружаемое отдельно от приложения: https://learn.microsoft.com/en-us/aspnet/core/mvc/models/file-uploads?view=aspnetcore-10.0 . Binary body в OpenAPI 3.1 обозначается `application/octet-stream: {}` по спецификации https://spec.openapis.org/oas/v3.1 .

## 4. Статусы и действия

| Ситуация | Ожидаемое поведение сервера |
|---|---|
| Кейс ещё `REGISTRATION_CLOSED` и не запущен | Участник не получает приватные stage-метаданные/файлы, даже если дата наступила. |
| `EXECUTING`, допущенная активная команда и доступный этап | Разрешён только текущий материал после проверки NDA. |
| Дедлайн сдачи прошёл, приём не закрыт | Сдача допускается, `isLate=true`. |
| Обычная точка закрыта вручную | Сдачи отклоняются `409`, прежние версии доступны по правам. |
| Отбор завершён | Невыбранная команда теряет доступ к будущим этапам, история остаётся. |
| Загрузка другого `applicationId`/`fileId` | Отказ `403/404`, никакой утечки метаданных и байтов. |
| Кейс в `FINAL_CLOSED` | Новые финальные сдачи отклоняются `409`. |

## 5. Открытые решения перед реализацией

1. **Решено TL:** SOLO допускается к ручному отбору по тем же правилам, что и TEAM; для него отдельная квота и список проходящих заявок.
2. **Решено TL:** NDA читает и подтверждает капитан TEAM или SOLO при подаче заявки; версия NDA должна быть зафиксирована на submit. Менять опубликованную версию без нового согласования нельзя.
3. **Дизайн-решение:** можно ли иметь несколько FINAL контрольных точек? В проекте предполагается одна; проверка при публикации требует согласования.
4. **Дизайн-решение:** кто и когда открывает следующие этапы — по дате, по завершению предыдущей точки или вручную? В любом случае старт кейса + права участника обязательны. Точная стратегия доступности требует согласования.
5. **Дизайн-решение:** время жизни staged-файла, максимальный размер, типы, сканер и очистка; DevOps/заказчик утверждают значения.
6. **Решено TL:** повторная заявка после REJECTED/WITHDRAWN запрещена; состав TEAM меняется только до подачи и замораживается после, а смена капитана остаётся отдельной подтверждаемой процедурой. Допустимые стадии передачи капитана уточнить в матрице прав.
7. **Дизайн-решение:** запрет преждевременного закрытия обычной точки и условие закрытия финального приёма (например, закрытие всех предшествующих контрольных точек) — требует решения; YAML не объявляет не согласованные временные ограничения обязательными.

## 6. Приёмочные проверки P0

- [ ] Только компания меняет этапы в `DRAFT/REVISION`; публикация блокирует изменение существенных условий.
- [ ] Без ручного старта файл/инструкция не видны в `workspace`, метаданных и `GET /files/{id}/content`.
- [ ] Только капитан TEAM и сам SOLO создают версию сдачи; другая роль получает 403.
- [ ] Версии 1,2,3 сохраняются, старые payload неизменны, повтор одного `Idempotency-Key` не создаёт дубль.
- [ ] После дедлайна до ручного закрытия — 201 и `isLate=true`; после закрытия — 409.
- [ ] Отбор выбирает не более N активных команд и не выполняется дважды без идемпотентного повтора.
- [ ] Выбывший / исключённый / чужая команда / гость не получают **будущие** private file metadata или содержимое при прямом запросе.
- [ ] NDA-политика доступна для ознакомления до принятия, а принятые версии аудируются; применение согласованной политики доступа протестировано.
- [ ] При недоступном storage/сканере файл не считается `READY` по умолчанию, корректные 5xx и отсутствие публичного доступа.
- [ ] Прогнан полный staging-сценарий: CASE → MODERATION → OPEN → ADMIT → CLOSE → START → VERSION 1/2 → SELECTION → VERSION AFTER DEADLINE → FINAL CLOSE.

**Статусы:** `UI Ready` означает интерфейс и согласованный mock, **не** реальный функционал. `Done (API)` только после интеграционных проверок, CI, прав и демонстрации работы сервера.

 
### Корректировка NDA-потока в 0.1.5-draft

Для обязательного NDA `GET /api/v1/cases/{caseId}/nda` должен быть доступен капитану команды / solo до отправки заявки. `POST /api/v1/applications/{applicationId}/submit` принимает `ndaAcceptance: { version, accepted: true }` и атомарно фиксирует подписанта, версию, время и состав. Отдельный `POST /api/v1/cases/{caseId}/nda/accept` удалён; подписи после допуска не требуются.

Соло-отбор реализуется тем же ручным `complete-selection`, отдельной `soloSelectionLimit` и идентификаторами заявок `passingSoloApplicationIds`. Автоматический рейтинг по баллам не предусмотрен.
